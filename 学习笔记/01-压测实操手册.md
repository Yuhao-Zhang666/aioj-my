# 压测实操手册（单机版 · k6）

> 配套文档：学长留下的 `DUAL_4C8G_50_USER_LOAD_TEST_2026-08-10.md`
> 目标：在 81 服务器上复现 50 用户混合 C++ 提交压测，理解每一步为什么这么做。

## 一、先搞清楚：为什么要重做这次压测

学长那份报告测的是**双节点**拓扑：

```
aioj_a 节点 (4c8g)          aioj_b 节点 (4c8g)
├── 网关 / 认证 / 题目        ├── judge-worker
├── AI / MySQL / Redis        └── sandbox (go-judge)
├── RabbitMQ
└── web 前后端
```

现在因为**费用原因**，两台合成一台（82），所有功能跑在**同一个 4c8g** 上。

**这不是"少了一台"，而是"资源竞争格局变了"：**

| 维度 | 双节点（学长的测试） | 单节点（现在要测的） |
|---|---|---|
| judge-worker + sandbox 的 CPU | 独占 b 节点 4 核 | 和网关/MySQL/auth 抢同一堆核 |
| 判题时 MySQL 会怎样 | 不受影响 | **判题高峰正好撞上提交高峰** |
| 内存 | 两节点各 8G，合计 16G | 只有 8G |
| Sandbox 是 privileged 容器 | 独占节点 | 和应用同机，安全面更大 |
| swap | b 节点没 swap | 单节点内存紧张会开始 swap，**判题延迟会爆炸** |

👉 **所以学长那份报告的结论对 82 不能直接套用。** 必须重测。
这正是老师给你这个任务的原因。

## 二、压测的基本原理（扫盲）

### 2.1 负载发生器为什么要"外部"

文档 README 里有一句硬规定：

> Run k6 from an external machine; running it on the server competes for the
> same CPU and invalidates capacity evidence.

翻译：**k6 不能跑在被测服务器上。**

为什么？假设 4 核服务器，k6 自己就要吃掉 1~2 核来发请求、算指标。
那么你测出来的"服务器能扛 50 人"，其实是"服务器 + 压测工具一起扛 50 人"。
数据就废了。

（学长当时是"同机但限制 k6 为 0.50 CPU"，并在报告里明确标注了这是**保守的、有限的证据**。
这就是严谨的做法——**不掩饰方法的缺陷，而是把它写进结论的局限性里**。）

**我们的优势**：你本地是 16 核 / 27.8 GB 内存，跑 k6 完全不虚。
从本机经公网打 81，比学长的同机测试**更接近真实课堂场景**。

### 2.2 k6 是什么

k6 是一个用 Go 写的压测工具，脚本用 JavaScript 写。

核心概念：

| 概念 | 含义 |
|---|---|
| **VU** (Virtual User) | 虚拟用户，一个 VU ≈ 一个独立的学生会话 |
| **iteration** | 一个 VU 执行一轮脚本 |
| **executor** | 调度策略。本项目用 `per-vu-iterations`（每个 VU 跑固定次数） |
| **threshold** | 通过/失败的门槛。不达标 k6 退出码非 0 |
| **Trend / Rate / Counter** | 指标类型：耗时分布 / 成功率 / 计数 |

### 2.3 为什么用 `per-vu-iterations` 而不是 `ramping-arrival-rate`

因为**"50 人同时登录并各交一题"**是**突发式**负载，不是持续的 QPS 压力。
每个 VU 只跑一次（iterations: 1），50 个 VU 同时启动 = 50 人同时点提交。
这才是课堂场景。

## 三、两个脚本的分工

### 3.1 `k6-login.js` —— 登录专项（只有登录，不交题）

- 50 个 VU，每个只登录一次
- **不加思考时间**，全力制造登录并发
- 目的：**单独测出认证服务的极限**

### 3.2 `k6-submissions.js` —— 提交专项（完整业务链路）

每个 VU 走完整流程：

```
登录 → 提交代码 → 轮询状态 → 直到终态 → 比对结果是否符合预期
```

关键设计（**这里体现了学长的工程水平，值得细看**）：

```javascript
// ① 用 __VU 序号决定用哪个账号，保证 50 个 VU 用 50 个不同账号
function accountForVu(vu) {
  return `${config.accountPrefix}${String(vu).padStart(3, "0")}`;
}
// 前缀 stuk5 + 3 位补零 → stuk501 ... stuk550

// ② 按配置决定每个 VU 交"标程"(期望 AC) 还是"死循环代码"(期望 TLE)
expected: index < problem.tle ? "TIME_LIMIT_EXCEEDED" : "ACCEPTED",

// ③ 轮询直到终态，而不是 sleep 固定时间
while (Date.now() - submitted.startedAt < config.pollTimeoutMs) { ... }
```

**第 ② 点是精髓**：为什么要故意交一份死循环代码？
因为**只测 AC 是不够的**。TLE 的判题路径完全不同——它要等超时计时器走完，
要把进程杀掉，要回收沙箱资源。如果只测 AC，你就漏掉了"超时杀死"这条最容易出 bug 的路径。

**第 ③ 点也是精髓**：轮询到终态才计时，得到的是**真实端到端延迟**，
而不是"提交成功就结束"的假指标。

### 3.3 安全阀

```javascript
const LOAD_TEST_ACK = "I_UNDERSTAND_THIS_CREATES_REAL_SUBMISSIONS";
if (config.acknowledgement !== LOAD_TEST_ACK) {
  configurationError(...);   // 不设这个环境变量，脚本直接拒绝运行
}
```

这叫 **"防误触保险"**。因为脚本会往生产库写真实提交，万一有人手滑跑了它，
数据库里就多几百条垃圾提交。

## 四、五个必须准备好的东西

| # | 变量 | 是什么 | 从哪来 |
|---|---|---|---|
| 1 | `BASE_URL` | 被测地址 | `http://81.70.53.200:5173` |
| 2 | `K6_PASSWORD` | 统一密码 | `12345678`（老师给的） |
| 3 | `K6_ACCOUNT_PREFIX` | 账号前缀 | `stuk5`（+3 位补零 = stuk501） |
| 4 | `K6_CODES_FILE` | **题目 ID + 标程代码** | ⚠️ 必须从服务器提取 |
| 5 | `AIOJ_LOAD_TEST_ACK` | 安全确认字符串 | 手写 |

### ⚠️ 第 4 项是关键难点

标程（正确答案的代码）在**服务器的数据库**里（`problem_solutions.content` 字段）。
k6 需要它才能提交"能 AC 的代码"。

**为什么不能自己写标程？** 因为：
1. 你写的代码可能过不了，导致期望 AC 实际 WA，指标全乱
2. 用错版本的标程可能和服务器测试数据不匹配
3. 文档明确要求："Production server data is the only source for test accounts, problem IDs, and standard solutions."

**正确的提取方式**：用学长的 `create-k6-accounts.sh` 里的 `write_codes_file()` 函数。
它会：
1. 从 MySQL 查出标程（用 `HEX()` 转成十六进制，避免编码/换行问题）
2. 用 Python 解码回 UTF-8
3. 自动配上一份**必然 TLE 的死循环代码**
4. 生成 `k6-submission-codes.json`

死循环代码长这样（这个设计很妙——不依赖题目内容，对任何题都必然超时）：

```c
#include <bits/stdc++.h>
using namespace std;
int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);
    volatile unsigned long long x = 1;
    while (true) {
        x = x * 1315423911ULL + 2654435761ULL;
    }
    return int(x);
}
```

## 五、测试阶梯：为什么不能一上来就打 50 人

学长用的阶梯（**这是标准做法，照抄**）：

| 阶段 | 负载 | 期望结果 | 目的 |
|---|---|---|---|
| ① AC 冒烟 | 1 条 AC | 2.2 秒 | 确认最基本链路通 |
| ② TLE 冒烟 | 1 条 TLE | 8.2 秒 | 确认超时路径通 |
| ③ 10 用户混合 | 8 AC + 2 TLE | 18.7 秒 | 小规模验证 |
| ④ 50 用户混合 | 40 AC + 10 TLE | 75.9 秒 | 正式测 |

**为什么必须从 1 条开始？**

因为如果 50 人一起上、失败了，你**根本不知道是哪坏了**。
而先跑 1 条，你能确认：
- 账号密码对不对
- 题目 ID 对不对
- 标程能不能 AC
- 提交接口通不通
- 判题队列动不动
- 轮询逻辑对不对

**一次只改一个变量**——这是排查问题的第一原则。

**50 用户那轮为什么不先跑 25？** 因为 50 是目标容量，10 → 50 是一个数量级内的合理跳跃。
但如果你想更稳，可以插一个 25。

## 六、指标怎么读（★ 最重要的部分）

### 6.1 四个成功率

| 指标 | 含义 | 门槛 |
|---|---|---|
| `aioj_login_success_rate` | 登录成功比例 | ≥ 95% |
| `aioj_submission_accepted_rate` | 提交被受理比例 | ≥ 95% |
| `aioj_poll_success_rate` | 轮询查状态成功比例 | ≥ 95% |
| `aioj_terminal_completion_rate` | 跑到终态的比例 | ≥ 95% |
| `aioj_expected_result_rate` | **结果符合预期**的比例 | ≥ 95% |
| `aioj_system_error_submissions` | 判题系统错误数 | **必须 = 0** |

### 6.2 `expected_result_rate` 为什么最重要

它检验的是：**该 AC 的真的 AC 了，该 TLE 的真的 TLE 了**。

如果 40 条标程里有 3 条变成了 WA，说明**测试数据或标程有问题**（不是性能问题，是正确性问题）。
这种情况比慢更严重——**判题判错了，整个平台就失去意义**。

### 6.3 延迟怎么看：P95 而不是平均值

| 统计量 | 含义 |
|---|---|
| avg（平均） | 会被极值拉偏，参考价值低 |
| **P95** | **95% 的请求都快于这个值** ← 主要看这个 |
| P99 | 最慢的 1%，看极端情况 |
| max | 单个最差情况 |

举例：平均 16.88 秒、P95 34.08 秒、最慢 36.34 秒。
意思是"大部分很快，但有一批确实等久了"。**P95 才反映真实体验。**

### 6.4 三个最容易忽略但极其重要的指标

| 指标 | 命令 | 为什么重要 |
|---|---|---|
| **RabbitMQ 队列深度** | 管理台 `15672` 或 `rabbitmqctl` | 测完队列必须**回落到 0**。不回 0 说明判题卡住了 |
| **容器重启/OOM** | `docker inspect -f '{{.RestartCount}} {{.State.OOMKilled}}'` | 有重启 = 内存不够，容量结论作废 |
| **swap 使用** | `free -h` | 一旦开始 swap，判题延迟会**暴涨几个数量级** |

## 七、★ 本次压测的核心假设：BCrypt 瓶颈

这是学长报告里**最有价值的发现**，我们这次要重点验证。

### 7.1 现象

| auth-service CPU 上限 | 50 并发登录 P95 |
|---|---|
| **0.50 CPU**（原配置） | **39.55 秒** 😱 |
| 4.00 CPU | 5.80 ~ 6.26 秒 |

### 7.2 根因

**BCrypt 是故意设计得"慢"的哈希算法。**

为什么故意慢？因为要防暴力破解密码。攻击者想每秒试几百万个密码，
BCrypt 让他每秒只能试几十个。这是**安全特性，不是 bug**。

`BCrypt cost 12` 意味着要做 2¹² = 4096 轮计算。一次校验大概要几十到上百毫秒。
50 个人同时登录 = 50 次 BCrypt 同时算。

而 `compose.yml` 里给 auth-service 的 CPU 上限是：

```yaml
auth-service:
  cpus: "0.35"     # 本地/dev 配置
```

服务器上是 `AUTH_CPUS=0.50`。**半个 CPU 核去做 50 次 BCrypt，当然要 40 秒。**

### 7.3 为什么不是连接池/网关/网络的问题

报告里已经用数据排除了：
- auth-service 第一轮 50 登录消耗约 **20.75 CPU 秒** ← 纯计算量
- cgroup 只新增一次节流、约 466 微秒 ← 说明一直在满负荷算，没被误限

**结论：瓶颈是 CPU 总工作量，加机器/加核才有效，调参数没用。**

### 7.4 不能作弊

报告里写得很硬：

> 不得把 BCrypt 降级作为达标手段。

意思是：**不能为了压测数据好看就把 cost 12 降到 4**。
那是拿安全性换指标，是自欺欺人。这条职业操守要记住。

### 7.5 对 82（单节点）的影响

双节点时，auth 至少不和 sandbox 抢 CPU。**合并到一台后：**
- sandbox 判题时要吃满 CPU（`cpus: "1.20"`）
- 学生登录高峰和判题高峰**可能重叠**
- MySQL、网关、problem-service 也都在抢

👉 **我们的预测：单节点上的登录 P95 会比双节点的 5.8~6.26 秒更差。**
这个预测对不对，就是本次压测的核心看点。

## 八、测前必查清单（Stop Line）

文档明确列出，**任何一条不满足就不能开测**：

- [ ] 运行中比赛 = 0
- [ ] 活跃运维异步任务 = 0
- [ ] 活跃 AI 草稿任务 = 0
- [ ] 活跃 Agent 异步任务 = 0
- [ ] 待判提交（QUEUED/RUNNING）= 0
- [ ] RabbitMQ 判题主队列 = 0
- [ ] RabbitMQ 死信队列（DLQ）= 0
- [ ] 50 个压测账号已启用
- [ ] 三道目标题可访问
- [ ] 网关和 judge 健康端点 = UP
- [ ] 所有 Compose 服务状态正常
- [ ] **swap 使用 = 0**
- [ ] 磁盘和内存余量充足

**为什么要查队列为空？** 因为如果本来就有提交在排队，
你测出来的"50 人排队 75 秒"里，有一部分是在排别人的队。数据被污染了。

**为什么要查没有比赛？** 因为比赛期间学生的真实提交会混进来，
而且比赛数据不能被污染。

## 九、⚠️ 在 81 上做这件事的特殊风险

81 和 82 不一样：**81 是老师在用的、有真实数据的系统**（数据库里有 700+ AC 提交、
35 道题、真实学生账号）。

在 81 上跑压测会：

| 副作用 | 严重性 |
|---|---|
| 往数据库写入 62 条测试提交 | 低（可清理） |
| 测试期间占用 CPU/内存，真实用户会变慢 | 中 |
| 如果内存爆了，可能 OOM 杀死容器 | **高**（影响老师的使用） |
| 如果磁盘满了，MySQL 可能损坏 | **高** |

**所以：**
1. **必须先问老师**，确认 81 上的数据可以接受测试提交
2. 测试前记下所有容器的 `RestartCount`，测后对比
3. 测试前记下磁盘余量，测后对比
4. 一旦发现 OOM/重启/swap 持续增长，**立即停止**

## 十、我们和学长做法的一个关键差异

| | 学长 | 我们 |
|---|---|---|
| k6 位置 | 81/82 **同机**，一次性容器，限 0.50 CPU | **你本机**（16 核/27.8G），经公网 |
| 网络路径 | 本机 Web 入口（`localhost`） | 公网 `81.70.53.200:5173` |
| 优点 | 无网络噪声，纯测服务端 | **不占用被测服务器 CPU**（更符合规范） |
| 缺点 | 占用被测机 CPU，数据偏保守 | 含公网延迟，且受你本地网络影响 |

**结论**：我们这次的数据**不能和学长的数字直接比**（方法不同）。
要对比，只能说"趋势"。这一点必须写进报告，这就是**严谨**。

## 十一、本机跑 k6 的命令模板

```powershell
# 目录约定（本机）
# D:\deepseek\load-test\  ← 存放 K6_ENV_FILE 和 K6_CODES_FILE

docker run --rm -i `
  -v "D:\deepseek\load-test:/scripts" `
  -e BASE_URL="http://81.70.53.200:5173" `
  -e K6_PASSWORD="12345678" `
  -e K6_ACCOUNT_PREFIX="stuk5" `
  -e K6_ACCOUNT_COUNT="50" `
  -e K6_ENV_FILE="/scripts/k6-load-test.env" `
  -e K6_CODES_FILE="/scripts/k6-submission-codes.json" `
  -e AIOJ_LOAD_TEST_ACK="I_UNDERSTAND_THIS_CREATES_REAL_SUBMISSIONS" `
  -e K6_RUN_LABEL="81-smoke-ac-r1" `
  -e P1_TOTAL="1" -e P1_TLE="0" `
  -e P2_TOTAL="0" -e P2_TLE="0" `
  -e P3_TOTAL="0" -e P3_TLE="0" `
  grafana/k6 run /scripts/k6-submissions.js
```

注意 `-v` 挂载：k6 需要读到那两个文件，所以必须把目录挂进容器。
`K6_ENV_FILE` / `K6_CODES_FILE` 要用**容器内的路径**（`/scripts/...`）。

## 四、工具链修复（本轮的重要产出）

### 问题：账号命名与脚本公式不兼容

`k6-login.js` / `k6-submissions.js` 构造账号的公式是：

```javascript
`${config.accountPrefix}${String(vu).padStart(3, "0")}`
```

`per-vu-iterations` 的 `__VU` **强制从 1 开始**，因此该公式只能生成
`k6stu001..050`（`prefix=k6stu`）这类以 001 起始的账号。
老师新建的 `stuk501..550` 无法表达。

实测确认：

| 账号 | HTTP | 说明 |
|---|---|---|
| `stuk501` | **200** | 真实存在 |
| `stuk5001` | 401 | 不存在 |
| `stuk1` | 401 | 不存在 |

### 修复方案

新增环境变量 `K6_ACCOUNT_START`（默认 `0`，**向后兼容**不改变既有行为）：

```javascript
accountStart: intEnv("K6_ACCOUNT_START", 0, 0, 99999),
...
return `${config.accountPrefix}${String(vu + config.accountStart).padStart(3, "0")}`;
```

并在 `setup()` 日志中输出实际账号区间（此前无此信息，导致排查绕路）：

```
accounts=stuk501..stuk550
```

用法：`K6_ACCOUNT_PREFIX=stuk` + `K6_ACCOUNT_START=500` + `K6_ACCOUNT_COUNT=50`

> **注**：老师若有其他脚本/文档依赖 `stuk5` 前缀（如打 JWT 令牌用于管理操作），
> 可能需同步调整。已在报告中标注，待确认。

## 六、数据分析：BCrypt 是瓶颈（证据链）

### 证据 1：分布形态——CPU 饱和特征

```
min    2,595 ms  ▏
avg    5,176 ms  ▏
med    5,480 ms  ▏
p(90)  5,779 ms  ▏
p(95)  5,828 ms  ▏
max    5,877 ms  ▏
```

50 个样本全部挤在 **2.6s ~ 5.9s** 的窄带内，**最大值仅为最小值的 2.3 倍**。

- 若是**网络抖动** → 分布会很散，并伴随超时/失败
- 若是**连接池排队** → 会看到明显的阶梯和超时
- 若是**CPU 饱和** → 所有请求都在同一个资源上排队，耗时**整齐地趋同** ✅

本轮的形态符合 CPU 饱和。

### 证据 2：与单请求的倍数关系

| 场景 | 耗时 | 倍数 |
|---|---:|---:|
| 1 人登录 | 0.348 s | 1× |
| 50 人并发 P95 | 5.828 s | **16.8×** |

若完全串行，应为 50×0.348 = 17.4 s。实测 5.83 s ≈ 17.4 / 3，
**与"4 个 CPU 核并行处理"的理论值吻合**（实际受调度损耗，略低于 4 倍加速）。

→ 说明瓶颈是**可并行的纯 CPU 计算**，而非串行资源（如单连接、单锁）。

### 证据 3：与学长双节点基准对比（趋势参考，非等效对比）

| 环境 | auth CPU | k6 位置 | 50 并发登录 P95 |
|---|---|---:|---:|
| 学长：双节点完整 Web 路径 | `AUTH_CPUS=4.00` | 同机（限 0.5 CPU） | 5.80 / 6.26 / 5.80 s（三轮） |
| **本轮：81 单机，经公网** | `4.00` | **外部机器** | **5.828 s** |

**81 的 5.828 s 落在学长三轮区间（5.80–6.26 s）之内，且为区间下沿。**

**解读**：
- 81 的 auth 登录路径**没有退化**，与学长调优后的双节点持平
- 本轮 k6 在**外部机器**（不受被测机 CPU 挤占），却未测出更快结果
  → 进一步支持"瓶颈在服务端 CPU 计算量，不在压测工具或网络"

> ⚠️ 方法差异：学长同机测试会**低估**服务器性能（k6 抢 CPU），
> 本轮外部测试理论上应**高估或持平**。实测却持平，说明公网往返延迟
> （约 +几十 ms）与学长同机的 CPU 挤占效应大致抵消。**不能据此断言 81 优于双节点。**

## 八、结论

### 可以支持的结论
1. 81 服务器（v1.0.4，单机 11 容器，4 核）在 `AUTH_CPUS=4.00` 下，
   **50 并发登录突发可以 100% 成功完成**，P95 = 5.83 s，无失败、无重启、
   无 OOM、无 swap 增长、无数据污染。
2. 该结果与学长双节点基准（5.80–6.26 s）持平。
3. 瓶颈确认是 **BCrypt(12) 的 CPU 计算总量**，不是网络、连接池或 cgroup 误限。

### 不能支持的结论（务必写清）
1. **不等于 82 的容量结论**：82 是合并单节点，sandbox 判题会与 auth 抢 CPU；
   81 本轮**未施加任何判题负载**，完全没测到这个竞争。
2. **不等于 50 人课堂 SLA**：仅测登录，未含浏览、提交、判题、比赛、SSE、AI。
3. **未达"P95 < 5 秒"**：5.828 s 未满足文档提出的"稳健 P95 小于 5 秒"目标。
4. 未覆盖公网客户端多样性与真实浏览器渲染。

### 后续建议
1. **先查 82 的 swap**：若与 81 同样有近 1 GB 占用，混合压测前必须处理。
2. **82 上必须做"登录 + 判题同时"的联合测试**：
   这才是合并单节点的真正风险点——sandbox 吃满 CPU 时，登录 P95 会变成多少？
3. **不要下调 BCrypt cost**：文档明确禁止（"不得把 BCrypt 降级作为达标手段"）。
   若必须达 P95<5s，应增加物理 CPU 或独立认证容量。
4. 在本轮基础上继续跑阶段③（AC 冒烟）→ ④（TLE 冒烟）→ ⑤（50 用户混合提交）。

## 九、复现命令

```powershell
# 前置：把 k6 脚本（含 K6_ACCOUNT_START 补丁）放在 D:\deepseek\load-test
docker run --rm -i -v "D:\deepseek\load-test:/scripts" `
  -e BASE_URL="http://81.70.53.200:5173" `
  -e K6_PASSWORD="<密码>" `
  -e K6_ACCOUNT_PREFIX="stuk" `
  -e K6_ACCOUNT_START="500" `
  -e K6_ACCOUNT_COUNT="50" `
  -e LOGIN_P95_MAX_MS="7000" `
  -e LOGIN_SUCCESS_MINIMUM="1" `
  -e HTTP_FAILURE_MAXIMUM="0.01" `
  -e K6_RUN_LABEL="81-login-50-r1" `
  -e MAX_DURATION="3m" `
  grafana/k6 run --summary-export /scripts/results/81-login-50-r1.json `
  /scripts/k6-login.js
```

> ⚠️ **k6 `--summary-export` 的坑**：该版本导出的
> `metrics.<name>.thresholds.<expr>` 布尔值**不代表阈值通过/失败**
> （通过时也可能为 `false`）。**判定必须看控制台的 ✓/✗ 与 k6 退出码**
> （退出码 `99` = 阈值不合格，`1` = 脚本异常，`0` = 全部通过）。

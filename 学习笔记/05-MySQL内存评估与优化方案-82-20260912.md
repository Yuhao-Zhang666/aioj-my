# 服务器 2（82.157.96.203）MySQL 内存现状评估与优化方案

| 项目 | 内容 |
|---|---|
| 报告日期 | 2026-09-12 |
| 被测服务器 | 生产环境 **82.157.96.203**（腾讯云单机，**4 vCPU / 8 GB**，Docker Compose 全栈同机） |
| 评估对象 | `aioj-mysql-1` 容器（MySQL 8.4，内存上限 **1.25 GiB**） |
| 触发原因 | 压测前基线检查发现该容器内存占用 **78.6%**，需评估是否影响即将进行的承载能力压测 |
| 评估方式 | 只读诊断（`docker stats`、`information_schema`、`SHOW STATUS`、MySQL 配置查询），**未修改任何配置、未重启任何容器** |
| **核心结论** | 内存占用高**不是**数据量或负载压力导致，而是 **`innodb_buffer_pool_size = 768 MB` 对当前 334 MB 的小库属过度配置**；该池**实际仅使用 48%**，存在 **384 MB 可回收的预留空间**。**压测前无需扩容**，建议按优先级调整配置 |

---

## 1. 背景

在准备对 82 服务器进行"比赛内提交"承载能力压测时，压测前基线检查（Stop Line）发现：

```
aioj-mysql-1    1006 MiB / 1.25 GiB    78.62%
```

对比另一台同规格服务器（81.70.53.200）：

```
aioj-mysql-1    527.3 MiB / 1.25 GiB   41.19%
```

**同为 4 vCPU / 8 GB、同为 MySQL 8.4、`innodb_buffer_pool_size` 完全相同（均 768 MB），但 82 的内存占用是 81 的 1.9 倍。**

本报告的目的是查清原因、评估风险、给出优化方案，供决策后执行。

---

## 2. 关键发现

### 2.1 发现一：`buffer pool` 实际只用了 48%

```
POOL_ID  pool_MB  used_MB  free_MB  used_pct
0        768      370      398      48.2%
```

**`innodb_buffer_pool_size` 配了 768 MB，但实际只缓存了 370 MB 数据，398 MB 处于空闲状态。**

佐证指标：

| 指标 | 实测值 | 含义 |
|---|---|---|
| `Innodb_buffer_pool_read_requests` | 21,366,521 | 总缓存读请求 |
| **`Innodb_buffer_pool_reads`** | **1,109** | 真正落盘读的次数——**占比 0.005%**，说明缓存远够用 |
| `Created_tmp_disk_tables` | **0** | 临时表从未撑爆内存写磁盘 |
| `Created_tmp_tables` | 1,053 | 临时表总量很少 |
| `Innodb_buffer_pool_pages_dirty` | 0 | 无脏页积压 |

**结论**：当前 MySQL 的工作集（working set）很小，768 MB 的缓存池**远超实际需要**。

### 2.2 发现二：内存高是"预留式分配"，不是"被数据撑满"

`innodb_buffer_pool_size` 是**预留式分配**——MySQL 启动时即向操作系统申请并占用该内存，与"实际缓存了多少数据"无关。

因此容器内存的构成是：

```
1006 MiB（docker stats 报告值）
  ├── 768 MiB   innodb_buffer_pool_size 预留（不可回收，即使仅用 370 MB）
  ├──  ~238 MiB MySQL 其他内部结构 + 页缓存（可部分回收）
  └── 剩余空间 = 1280 MiB - 1006 MiB = 274 MiB
```

**这解释了为什么 82 比 81 高**：两台 `buffer pool` 都是 768 MB，但 **82 的数据量更大，缓存填充更充分**，导致其他内存项（页缓存、字典缓存等）也相应增长。

| 项目 | 81 | 82 | 差异 |
|---|---|---|---|
| `ai_oj_next` 数据量 | 203 MB | **334 MB** | +65% |
| 最大单表 | `ai_retrieval_chunks` 83 MB | `contest_scoreboard_snapshots` **162 MB** | 2.0× |
| `/var/lib/mysql` 磁盘 | 672 MB | **966 MB** | +294 MB |
| 最大 binlog 文件 | 87 MB | **283 MB** | 3.3× |
| docker stats 内存 | 527 MiB | **1006 MiB** | +479 MiB |

### 2.3 发现三：已排除的嫌疑

| 嫌疑方向 | 实测证据 | 判定 |
|---|---|---|
| 连接数过多 | `Threads_connected=7`，`Max_used_connections=13`（上限 100） | ❌ 无关 |
| 临时表溢出 | `Created_tmp_disk_tables=0` | ❌ 无关 |
| 数据量超出缓存容量 | 数据 334 MB < 池 768 MB | ❌ 不是主因 |
| 查询堆积 | `Threads_running=2` | ❌ 无关 |
| 脏页/刷盘积压 | `Innodb_buffer_pool_pages_dirty=0` | ❌ 无关 |

## 4. 优化方案对比

| # | 方案 | 可节省 | 代价 / 风险 | 是否需重启 MySQL |
|---|---|---|---|---|
| **A** | **`innodb_buffer_pool_size` 768 → 384 MB** | **约 384 MB** | **极低**——当前数据仅 334 MB，384 MB 池仍可容纳全部热数据 | 需要 |
| **B** | 清理 `contest_scoreboard_snapshots` 历史数据 | 100–200 MB（含页缓存释放） | 中——需业务确认历史快照是否仍需保留 | 不需要 |
| **C** | 关闭 `performance_schema` | 50–150 MB（**需精确复核**，见 §6） | 低——失去细粒度性能诊断能力（当前未被使用） | 需要 |
| **D** | `max_connections` 100 → 50 | 约 50–100 MB（每条连接数 MB） | 中——并发高时可能拒绝连接 | 需要 |
| **E** | 抬高容器内存上限 1.25 → 1.5 GiB | 250 MB（相对缓解） | 低——宿主机 `available` 3.74 GB，余量充足 | 需要（重建容器） |
| **F** | 启用 swap 兜底 | — | **高——会导致判题延迟数量级放大，不建议** | — |

### 4.1 方案 A 的可行性论证（推荐）

**为什么"调小缓存池"反而几乎没有性能损失：**

| 论据 | 数据 |
|---|---|
| 数据总量 | 334 MB |
| 建议池大小 | 384 MB（> 334 MB，**仍可容纳全部数据**） |
| 当前实际使用 | 370 MB（< 384 MB） |
| 磁盘读占比 | 0.005%（`reads / read_requests`） |

→ 改为 384 MB 后，**当前热数据仍可全部驻留内存**，性能影响可忽略，而**直接释放 384 MB 预留内存**。

**继续优化空间**：若后续数据增长，可在数据量超过池容量时再评估是否上调。

### 4.2 方案 B 的收益

清理 `contest_scoreboard_snapshots`（162 MB）后：

- InnoDB 需要缓存的数据页减少约 **48%**（162 / 334）
- 若数据量降至约 172 MB，则 `buffer pool` 可进一步调小到 **256 MB** 仍够用
- **方案 B + 方案 A 组合，理论上可释放约 500 MB**

## 5. 风险评估

### 5.1 当前状态是否安全

| 场景 | 内存预期 | 判定 |
|---|---|---|
| 日常运行（无压测） | 稳定在 1006 MiB，余量 274 MiB | ✅ **安全** |
| 低强度压测（10 并发，约 50 条提交） | 增量小，余量足够 | ✅ **可安全执行** |
| 完整梯度压测（10/30/50 并发，约 420 条提交） | 提交写入增加 → 页缓存与内部结构增长 | ⚠️ **存在触及上限的可能，需全程监控** |

### 5.2 触及上限的后果链路

```
内存真占用逼近 1.25 GiB
  → 内核回收可回收页缓存（性能下降，磁盘 IO 增加）
  → 仍不足
  → cgroup OOM killer 杀掉 MySQL 进程
  → 容器按 restart: unless-stopped 自动重启（服务中断数十秒）
  → 重启期间：学生提交 / 登录 / 榜单刷新全部失败
  → 可能新增"永久判题中"的丢单（与已知死锁缺陷同类后果）
```

**重要澄清**：内存不足**不会**导致"无法创建比赛"。创建比赛为单行插入操作，与内存水位无关。风险在于**整体写操作中断**，而非单一功能不可用。

### 5.3 为什么"改配置"必须谨慎

本报告涉及的所有方案（除 B 外）都需要**重启 MySQL**，而 82 是**老师的生产环境**：

1. 重启期间全站写操作中断
2. 若此时有真实学生使用，影响直接可见
3. 需在**低峰期**执行，且**执行前备份**

## 6. 待复核项（数据置信度说明）

1. **`performance_schema` 占用值为初步数据**：诊断脚本输出的 `performance_schema 总占用 = 1270.9 MB` **明显与容器总内存（1006 MiB）矛盾**，判断为**查询口径问题**（该视图统计的是历史累计分配而非当前驻留）。**方案 C 的实际收益需用更精确的方法复核后再决策**。
2. `contest_scoreboard_snapshots` 的业务属性（是否仅含测试赛快照）需业务方确认。
3. `ai_retrieval_chunks` 的重建成本需评估。
4. cgroup 层面的"可回收页缓存 vs 不可回收占用"拆分**未能取得**（容器使用 cgroup namespace，容器内无法读取自身 cgroup 路径），故 §2.2 的 238 MiB 为推算值。

## 7. 建议

### 7.1 若不调整任何配置

**可以执行低强度压测**（10 并发），但必须：

- 全程监控 `aioj-mysql-1` 内存与宿主机 `available`
- 设定停止红线：**宿主机 `available` < 800 MB，或 MySQL 容器内存 > 1150 MiB**
- 一旦触及红线立即终止压测

### 7.2 若希望更稳妥（推荐）

**按以下顺序，在低峰期执行，每步之间观察：**

| 步骤 | 操作 | 预期释放 | 风险 |
|---|---|---|---|
| 1 | 备份数据库 | — | 必须 |
| 2 | 清理 `contest_scoreboard_snapshots` 历史数据（方案 B） | 100–200 MB | 无需重启 |
| 3 | `innodb_buffer_pool_size` 768 → 384 MB（方案 A） | 384 MB | 需重启 |
| 4 | 复核并视情况关闭 `performance_schema`（方案 C） | 待复核 | 需重启 |
| 5 | 重跑本报告诊断，确认内存降至 **600 MiB 以下** | — | — |
| 6 | 再执行完整梯度压测 | — | — |

**执行步骤 3 后，MySQL 内存预期从中降至约 620 MiB（50% 以下），为压测留出充足余量。**

### 7.3 不建议

- ❌ **抬高容器上限但不调小 buffer pool**——治标不治本，浪费宿主机内存
- ❌ **依赖 swap 兜底**——会显著放大判题延迟
- ❌ **未备份直接改配置**——生产库操作必须留退路

## 8. 附录：诊断命令

```bash
# 内存总览
docker stats --no-stream --format 'table {{.Name}}\t{{.MemUsage}}\t{{.MemPerc}}' | grep -E 'NAME|mysql'
free -m

# 关键配置
docker exec -it aioj-mysql-1 sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "
  SELECT @@innodb_buffer_pool_size/1048576 AS buffer_pool_MB,
         @@performance_schema AS perf_schema,
         @@max_connections AS max_conn,
         @@tmp_table_size/1048576 AS tmp_MB;""'

# buffer pool 实际使用率（关键指标）
docker exec -it aioj-mysql-1 sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "
  SELECT POOL_ID,
         ROUND(POOL_SIZE*@@innodb_page_size/1048576) AS pool_MB,
         ROUND(DATABASE_PAGES*@@innodb_page_size/1048576) AS used_MB,
         ROUND(100*DATABASE_PAGES/(DATABASE_PAGES+FREE_BUFFERS),1) AS used_pct
  FROM information_schema.INNODB_BUFFER_POOL_STATS;"'

# 大表体积
docker exec -it aioj-mysql-1 sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "
  SELECT table_name, ROUND((data_length+index_length)/1048576,1) AS MB, table_rows
  FROM information_schema.tables WHERE table_schema=\"ai_oj_next\"
  ORDER BY (data_length+index_length) DESC LIMIT 10;"'

# 内存压力指标
docker exec -it aioj-mysql-1 sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "
  SHOW GLOBAL STATUS WHERE Variable_name IN (
    \"Created_tmp_disk_tables\",\"Innodb_buffer_pool_reads\",
    \"Innodb_buffer_pool_read_requests\",\"Threads_connected\",\"Max_used_connections\");"'
```

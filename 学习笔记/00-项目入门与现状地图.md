## 二、项目是什么

**AIOJ = AI 原生在线判题平台**（AI-powered Online Judge），面向高校教学。

一句话理解：**老师出题 → 学生做题/交代码 → 服务器沙箱判题 → AI 答疑和复盘**。

"AI 原生"的意思是：AI 不是外挂一个聊天框，而是内置到出题、答疑、复盘、学情画像的全流程里。

### 教学全链路

| 阶段 | 功能 |
|---|---|
| 课前 | AI 辅助出题、生成题目草稿（题面+标程+暴力解+数据生成器） |
| 课中 | 学生练习、AI 助教答疑（带比赛防作弊）、比赛运行 |
| 课后 | 异步判题、赛后 AI 复盘、学习画像 |

### 4.2 一次"交题"的完整数据流

```
学生点提交
  → 前端把代码 POST 到网关 /api/...
  → 网关鉴权（JWT）
  → problem-service 校验题目、保存 submission 记录
  → 往 RabbitMQ 发一条判题消息
  → judge-worker 从队列取出
  → 从 problem-service 拉取测试点 → 下载到 /aioj/cases 卷
  → 调用 sandbox 的 /execute 接口，在容器里编译+运行
  → 比对输出，得到 AC / WA / TLE / MLE / RE / CE
  → 结果写回 MySQL
  → 前端轮询或 SSE 拿到结果
```

**这条链路你要能背下来**，它是整个项目的主动脉。

### 4.3 AI 答疑（Agent Core V3）的核心思想

白皮书里有一句话是整个项目的灵魂：

> **模型是不可信规划器，服务器是可信控制面。**

翻译成人话：不要相信大模型的输出。模型只能说"我想调用某个工具"，但**能不能调用、能看什么数据、能不能把答案给学生**，全部由服务器决定。

配套设计：
- **Turn（轮次）**：每次问答是一个有唯一 ID 的事务，可重试、有终态、异步生成摘要
- **上下文分层**：Bootstrap → Turn摘要 → Episode摘要 → 原始证据回取 → 精确检索兜底
- **工具控制面**：每次工具调用都要重新检查身份/场景/参数 schema/数据可见性/预算
- **四层比赛安全**：参赛判定 → 策略快照 → 问题匹配 → 输出检查（防止比赛中套答案）
- **记忆 Claim 机制**：模型只能提"候选记忆"，必须用户确认才生效，防止幻觉污染用户档案

## 六、部署上云：完整链路（★ 回答"我推送上云要不要指向我的仓库"）

### 6.0 一句话结论

> **部署不依赖 Git 仓库地址，依赖的是「Docker 镜像存在哪」。**
> 你要用自己的账号部署，就必须把镜像发布到**你自己的** GHCR 命名空间，
> 然后改两个文件里的命名空间；光换 Git remote 是**没用的**。

### 6.1 完整链路（5 步）

```
① 你在 GitHub 上创建 Release（必须打 vX.Y.Z 格式的 tag）
        │
        ▼
② GitHub Actions 触发 .github/workflows/release.yml
        │  · 校验：tag 必须是 vX.Y.Z，且该提交必须是 origin/master 的祖先
        │  · 并行构建 8 个镜像（gateway/auth/problem/ai/judge-worker/sandbox/web-user/web-admin）
        │  · 推到 GHCR：ghcr.io/<命名空间>/aioj-<service>:vX.Y.Z
        │  · 生成 SBOM + 构建证明
        ▼
③ manifest 任务把 8 个镜像的 digest 汇总成 image-manifest.json，
   连同 deployment-bundle.tar.gz（含 compose.production.yml）一起**作为 assets 挂到 Release 上**
        │
        ▼
④ deploy 任务 SSH 登录生产服务器，执行受限命令：
        ssh aioj-deploy@<host> "deploy v1.0.4 <manifest_sha256>"
        │  · 需要 environment: production 的人工审批（GitHub 保护环境）
        │  · 需要 4 个 secrets：DEPLOY_SSH_HOST / DEPLOY_SSH_PRIVATE_KEY /
        │                     DEPLOY_SSH_KNOWN_HOSTS / （+ GITHUB_TOKEN 自动）
        ▼
⑤ 服务器上 /usr/local/sbin/aioj-deploy 干活：
        · 从 release_url 下载 image-manifest.json 和 deployment-bundle.tar.gz
        · 校验 sha256
        · 校验镜像地址必须匹配 ^ghcr\.io/xueyunji/aioj-(...)$
        · 用 manifest 里的 digest 生成 deploy.env（GATEWAY_IMAGE=... 等 8 个变量）
        · docker compose pull && up -d
        · 跑 /usr/local/sbin/aioj-health-check 做健康验证
        · 失败 → 自动用 deploy.previous.env 回滚镜像
        · 成功 → 写入 /opt/aioj/CURRENT_RELEASE
```

### 6.2 "生产 Compose" 怎么认镜像

这解答了你之前的疑惑——**Compose 文件里根本没写死 ghcr.io/mubai0628**：

```yaml
# deploy/compose.production.yml 里是这样写的
image: ${AUTH_IMAGE:?AUTH_IMAGE must be an immutable GHCR digest}
image: ${PROBLEM_IMAGE:?...}
image: ${SANDBOX_IMAGE:?...}
...
```

镜像地址是从 **环境变量** 注入的。而 `deploy.env` 就是这些变量的来源：

```
GATEWAY_IMAGE=ghcr.io/mubai0628/aioj-gateway@sha256:5dec5540...
AUTH_IMAGE=ghcr.io/mubai0628/aioj-auth@sha256:0e87c829...
...（共 8 个）
```

**所以"81 上跑的是学长的镜像不是老师的代码"这个现象，本质是：那份 `deploy.env` 里的地址指向学长命名空间。**
但注意——镜像是学长的**仓库地址**，里面的**代码内容**是老师发布的 v1.0.4 构建出来的（老师用自己的 GitHub Actions 构建时，推送目标被设成了 `ghcr.io/xueyunji/...`？不，见下）。

> 🔍 实测澄清：81 上的 8 个镜像全部是 `ghcr.io/mubai0628/aioj-*`（学长命名空间），
> 而老师 `release.yml` 里写的是 `ghcr.io/xueyunji/aioj-*`，`aioj-deploy` 也只接受 `xueyunji` 命名空间。
> 说明 **81 这套环境不是用老师现在的自动化流程部署的**，是更早的手工/半自动部署留下的

### 6.4 ⚠️ 三个必须知道的现实障碍

**障碍 A：你不能把老师的仓库 fork 成自己的仓库。**
`Yuhao-Zhang666/aioj` 已经存在，而且它 fork 的是**学长**的仓库。
GitHub **不允许 fork 自己的 fork**，也**不允许**把已有仓库改成另一个仓库的 fork。

→ 解决办法：**新建一个空仓库**（比如 `aioj-my`），然后把老师的代码 `git push` 进去。
注意这样它就**不是 fork**，无法用 GitHub 的 "Sync fork" 按钮，以后同步要手动 `git remote add` + `merge`。

**障碍 B：`release.yml` 要求 tag 提交必须是 `origin/master` 的祖先。**

```bash
git fetch origin master
git merge-base --is-ancestor "$GITHUB_SHA" origin/master
```

你现在的分支叫 `learning/deploy-v0.1.7`，而你本地的 `main` 比 `origin/main` **落后 2 个提交**。
所以**发布之前必须先理清分支**，把要发布的提交放到默认/`master` 分支上。

**障碍 C：`aioj-deploy` 脚本必须在服务器上以 root 运行，而且服务器要有 SSH 强制命令门禁。**
需要：
- 服务器上有个 `aioj-deploy` 用户
- 它的 `~/.ssh/authorized_keys` 里用 `command="/usr/local/sbin/aioj-deploy-gate"` 限制只能执行 deploy
- GitHub 仓库里配好 4 个 secrets
- 建一个 `production` Environment 并开启 required reviewers

### 7.1.1 ★ 第一个真实 Bug：健康检查耐心不够（本次会话已修）

**现象**：按手册的命令启动，`auth-service` 永远变成 `unhealthy`，然后 `gateway-service`
因为 `depends_on: auth-service: condition: service_healthy` **直接放弃启动**，
最终 web 两端也起不来。报错：

```
dependency failed to start: container aioj-xueyun-auth-service-1 is unhealthy
```

**排查过程（这就是你要学的"看日志定位问题"）**：

1. `docker logs <auth容器>` 看尾部 → 发现它**根本没崩**：
   ```
   HikariPool-1 - Start completed.
   Flyway: Successfully validated 65 migrations
   Flyway: Schema `ai_oj_next` is up to date.
   Tomcat initialized with port 8201
   Started AuthServiceApplication in 146.297 seconds
   ```
2. 进容器直接打健康接口 → `{"status":"UP"}` —— **服务是好的**
3. 于是问题不在服务，在**健康检查的判定规则**

**根因**：原配置是

```yaml
healthcheck:
  interval: 10s      # 每 10 秒查一次
  retries: 12        # 连续失败 12 次判为 unhealthy
                   # → 总窗口 = 10 × 12 = 120 秒
```

而 `auth-service` 冷启动要 **146 秒**（Spring 上下文初始化就花了 49 秒，
再加上 Flyway 校验 65 个迁移、Sentinel 初始化，都慢）。

**120 秒的窗口 < 146 秒的启动时间 → 必然误判。**

**修复**：给健康检查加 `start_period` 宽限期。它的语义是：
> "容器刚启动的这段时间内，健康检查失败**不计数**。"

```yaml
healthcheck:
  interval: 10s
  timeout: 5s
  retries: 12
  start_period: 180s   # ← 新增：前 180 秒内的失败不计入 retries
```

**影响范围**：加在全部 5 个 JVM 服务上（gateway / auth / problem / ai / judge-worker）。
`mysql`、`redis`、`rabbitmq` 用 `retries: 10` 且启动快，`sandbox` 是 Go 写的秒起，都不需要。

**验证方式**：
```powershell
docker compose ... config | Select-String start_period   # 应出现 5 次
```

**还没提交**：这个改动目前只在你本地工作区（`git diff` 能看到），
建议作为你的**第一个 commit** 提交上去。这是你的练手素材。

> **这个 bug 的价值**：它是"配置缺陷"而不是"代码缺陷"的典型案例。
> 代码完全正确，是运维参数配错了。真实项目里这类问题非常多，
> 而排查它的方法（**先看日志确认服务本身状态，再怀疑外围判定逻辑**）是通用的。

## 十一、安全红线（新手最常犯）

1. **`.env` 绝对不能提交**。里面有 MySQL 密码、JWT 密钥、DeepSeek API Key。它已经在 `.gitignore` 里了，别手动 `git add -f`。
2. **`*.pem` 私钥不能提交**。`.gitignore` 也覆盖了。
3. **不要在 81 上乱 `docker compose down -v`**，那会删掉所有数据和测试用例。
4. **不要直接 push 到老师的仓库**。先 push 到自己的 fork。
5. **改代码前先建分支**，别在 `learning/deploy-v0.1.7` 上直接改。
6. 81 磁盘已用 67%，别在上面下载大文件。

## 十二、名词表（先混个脸熟）

| 名词 | 一句话解释 |
|---|---|
| OJ | Online Judge，在线判题系统。你交代码，它跑测试数据判对错 |
| 网关 (Gateway) | 所有请求的统一入口，负责转发、鉴权、限流 |
| 微服务 | 把一个大系统拆成多个小服务，各自独立部署 |
| JWT | 一种登录凭证（一个签名过的字符串），前端每次请求都带上 |
| MQ / RabbitMQ | 消息队列。生产者丢消息进去，消费者慢慢取出来处理，用来削峰解耦 |
| 沙箱 (Sandbox) | 隔离的代码执行环境。判题必须用沙箱，否则学生交个删库代码就完了 |
| go-judge | 一个用 Go 写的判题沙箱实现 |
| Docker 镜像 / 容器 / 卷 | 镜像=安装包，容器=运行起来的实例，卷=持久化数据的地方 |
| Docker Compose | 用一个 yml 文件同时管理多个容器 |
| profile | Compose 里的服务分组开关 |
| digest | 镜像内容的 sha256 指纹，比 tag 更精确，生产用它固定版本 |
| Flyway | 数据库版本迁移工具，把建表语句当代码管理 |
| AC / WA / TLE / MLE / RE / CE | 判题结果：通过 / 答案错 / 超时 / 超内存 / 运行错误 / 编译错误 |
| Agent | 能自己决定调用工具的 AI 程序（不是单纯一问一答） |
| Prompt Injection | 提示词注入。用户用话术骗 AI 越权，本项目重点防御对象 |
| RAG | 检索增强生成。先查资料再让 AI 回答，减少胡说 |
| SBOM | 软件物料清单，记录镜像里有哪些依赖，供应链安全用 |
| 幂等 | 同一个操作执行多次，结果和执行一次一样 |
| 对拍 | 用暴力解和标程跑同样的数据，比对结果，验证标程正确性 |

## 4. 测试方法

### 4.1 用户行为模型

每个虚拟用户（VU）代表一名参赛学生：
登录（token 在 VU 内复用，不重复登录）→ 循环浏览比赛列表 / 场次详情 / 比赛题目 / 榜单 /

（C++ 70% / Python 30%）→ 提交后每 **500 ms** 轮询一次判题结果直到终态。

**提交请求体**（比赛模式）：

  "problemId": "<题库题目 ID>",
  "language": "cpp",
  "code": "<模板代码>",
  "contestId": "<比赛 ID>",
  "contestRunId": "<场次 ID>",

## 6. 死锁专项排查

### 6.1 背景

同规格服务器 2（82）在 `JUDGE_CONCURRENCY=2` 下曾出现：

```
ERROR Judge failed submission=... language=python queueWaitMs=188 judgeWallMs=768
      errorType=DeadlockLoserDataAccessException
### Cause: com.mysql.cj.jdbc.exceptions.MySQLTransactionRollbackException:
      Deadlock found when trying to get lock; try restarting transaction
      ; sending to DLQ
```

即：判题完成后**写回结果到 MySQL 时发生事务死锁**，Spring 抛 `DeadlockLoserDataAccessException`，
而代码**没有重试**，任务被送入死信队列 → **实际丢单**。

### 6.2 本轮检测方法

压测结束后对 judge-worker 日志做专项统计（近 1 小时窗口，覆盖全部三档）：

```bash
docker logs --since 1h aioj-judge-worker-1 2>&1 | grep -c 'Judge failed'
docker logs --since 1h aioj-judge-worker-1 2>&1 | grep -c 'Deadlock'
docker logs --since 1h aioj-judge-worker-1 2>&1 | grep -c ' ERROR '
docker logs --since 1h aioj-judge-worker-1 2>&1 | grep -c 'sending to DLQ'
```

### 6.3 检测结果

| 指标 | 81（`JUDGE_CONCURRENCY=1`） | 82（`JUDGE_CONCURRENCY=2`） |
|---|---|---|
| 提交总数 | 420 | 391 |
| **`Deadlock` 次数** | **0** | **1** |
| `Judge failed` 次数 | **0** | 1 |
| `sending to DLQ` 次数 | **0** | 1 |
| 真实 `ERROR` 级别 | **0** | 0（另有 9 行为该异常堆栈的 `Deadlock` 子串） |
| `SYSTEM_ERROR` | **0** | 0 |
| 死信队列最终深度 | **0** | 0 |

### 6.4 结论

1. **`JUDGE_CONCURRENCY=1` 下未出现任何死锁**：同一判题位串行执行，不存在两个事务并发写回
   同一批行的情形，**结构性排除了该死锁**；
2. **死锁与 `JUDGE_CONCURRENCY=2` 强相关**：并发为 2 时，两条判题线程可能以不同顺序获取
   同一批行的锁，MySQL 检测到循环等待后回滚其中一方；
3. **该缺陷的严重性在于"静默丢单"**：只丢 1 单、不触发 `SYSTEM_ERROR`、不影响其余提交，
   极难在监控指标上发现；但真实比赛中表现为"某学生提交后永远没有结果"；
4. **建议后端修复**：为结果写回事务增加**死锁重试**（捕获 `DeadlockLoserDataAccessException` /
   `MySQLTransactionRollbackException` 后有限次重试），而不是直接进 DLQ。

## 7. 承载能力结论

### 7.1 与前一轮同服务器基线对照

| 指标（50 并发档） | 前一轮（普通提交） | 本轮（比赛提交） | 变化 |
|---|---|---|---|
| 提交数 | 201 | **232** | +15% |
| 判题吞吐 | 0.55 份/秒 | **0.77 份/秒** | **+40%** |
| `judgeWallMs` 平均 | 1 640 ms | **1 225 ms** | −25% |
| `queueWaitMs` 平均 | 25 684 ms | **4 999 ms** | **−81%** |
| `queueWaitMs` p95 | 92 872 ms | **14 317 ms** | **−85%** |
| `queueWaitMs` 最大 | 107 221 ms | **18 527 ms** | **−83%** |
| `submit` p95 | 94 ms | **70 ms** | −26% |
| 死锁 | 未检测 | **0** | — |

> ⚠️ 两轮数据**不可直接互推容量**：客户端轮询行为不同（前一轮 50 并发档产生 17 045 次轮询，
> 是"判题慢→频繁刷新"的正反馈放大）。上表仅说明方向性趋势，不作为严格对照实验。

### 7.2 核心结论

以"每名学生平均每分钟提交 1 次"为基准（提交速率 = 人数 ÷ 60）：

| 在线人数 | 提交速率 | 实测表现 | 判定 |
|---|---|---|---|
| 10 人 | 0.17 份/秒 | 判题等待平均 5.0 s | ✅ 轻松 |
| 30 人 | 0.50 份/秒 | 判题等待平均 5.0 s | ✅ 舒适 |
| **50 人** | **0.83 份/秒** | **判题等待 p95 14.3 s、最长 18.5 s；232/232 全部出结果** | ✅ **可稳定承载** |

1. **判题吞吐天花板 ≈ 0.77–0.82 份/秒**（`JUDGE_CONCURRENCY=1`），实测达理论值 **93%**；
2. **50 人同时在线提交可稳定承载**：零丢单、零死锁、零 `SYSTEM_ERROR`、零重启/OOM，
   表现为"提交后 15–18 秒内出结果"；
3. 浏览器 / 网关 / 数据库 / 鉴权**完全不是瓶颈**（全部 p95 ≤ 130 ms，0 错误）；
4. **瓶颈唯一且明确：`JUDGE_CONCURRENCY=1` 这道判题闸门**，整机资源仅用零头；
5. 瓶颈排序：**判题链路 ≫ 登录（BCrypt）> 网页 / 网关 / 数据库**。

### 7.3 对"提高判题并发"建议的修正（重要）

前一轮报告 §7 建议将 `JUDGE_CONCURRENCY` 由 1 提到 2，预期吞吐翻倍。
**本轮实测数据不支持该建议：**

| 对照项 | 81（并发 = 1） | 82（并发 = 2） |
|---|---|---|
| 判题吞吐 | **0.77 份/秒**（理论值 93%） | 0.55 份/秒（理论值 **45%**） |
| `judgeWallMs` 平均 | **1 225 ms** | 1 640 ms |
| 死锁 | **0** | **1（丢单进 DLQ）** |
| 结论 | ✅ 稳定、高效 | ⚠️ 更慢、且引入丢单 |

**判读**：
1. **并发 = 2 反而吞吐更低**（0.55 < 0.77），说明吞吐损失并非来自判题并行度，
   而是来自并发引入的**锁竞争与事务冲突开销**——并发把"串行等待"换成了"锁等待 + 回滚"；
2. 并发 = 2 **额外引入死锁丢单**，这是正确性缺陷，不可接受；
3. **在引入死锁重试并实测验证之前，不应将 `JUDGE_CONCURRENCY` 提高到 2 或以上。**

> 若确需提升吞吐，**优先方向**是消除每份提交在判题之外的开销（测试点获取、评分写库次数、
> 编译开销），而非提高并发。

## 8. 已知局限（结论适用范围）

1. **提交内容为固定模板代码**（与题目无关），全量落入 `WRONG_ANSWER` / `RUNTIME_ERROR`。
   判题工作量（编译 + 运行全部测试点）真实，但**不代表真实题解的判题特征**；
2. **单档仅约 5 分钟**，未做长稳定性（> 1 小时）与内存/连接泄漏验证；
3. **账号池上限 50**，未验证 50 以上并发；
4. **未覆盖**：测试点极多 / 含子任务 / 带 checker 的重型题目、多语言混压、AI 调用并发、
   榜单高频刷新、故障注入与恢复；
5. 压测客户端位于公网，接口延迟含公网往返（基线约数十毫秒），未把网络与服务端耗时完全分离；
6. **swap 基线非 0**：压测前已用 989 MB（逐进程归因：mysqld 355 MB、ai-service 133 MB、
   problem-service 101 MB 等），属 85 天连续运行累积的内存压力痕迹，非活跃换页
   （宿主 `available` 4.1 GB，压测前后 swap 未增长）。**若在 82 上出现活跃换页，
   判题延迟会被显著放大，结论需重估**；
7. F2（`assertCanView` 的 `visibility=null` 403）本轮**未修复后端**，仅由脚本绕开；
   比赛详情的**真实学生端页面**是否受该缺陷影响，需前端链路单独验证。

## 9. 优化建议

| 优先级 | 措施 | 依据 | 预期收益 |
|---|---|---|---|
| **高** | **维持 `JUDGE_CONCURRENCY=1`**，不得在修复死锁前提高到 2 | 82 在并发 2 下吞吐更低（0.55 vs 0.77）且出现死锁丢单 | 规避丢单风险 |
| **高** | 为判题结果写回增加**死锁重试**，替代直接进 DLQ | 82 日志中的 `DeadlockLoserDataAccessException` | 消除静默丢单 |

#### F1 详述（本轮最有价值的发现）

**现象**：三档压测全部返回 `submit | http404:resource.notFound`，成功率 **0%**。

**根因**：`GET /api/v1/contests/{id}/runs/{runId}/problems` 返回的 JSON 中，`id` 与
`contestProblemId` 是**两个不同的值**：

```
id                = 2098595608607510530   （场次题目快照行 ID）
contestProblemId  = 2098595065671634946   （contest_problems 表主键）
problemId         = 2090980354876690434   （题库题目 ID）
```

后端 `ContestService.resolveSubmissionContext()` 按 **`contest_problems.id`** 查询：

```java
ContestProblemEntity contestProblem = contestProblemMapper.selectOne(
    new LambdaQueryWrapper<ContestProblemEntity>()
        .eq(ContestProblemEntity::getId, contestProblemId)
        .eq(ContestProblemEntity::getContestId, contestId));
```

**数据库交叉验证**：

| 查询 | 命中行数 |
|---|---|
| `... WHERE id = 2098595608607510530`（API 的 `id`） | **0** |
| `... WHERE id = 2098595065671634946`（API 的 `contestProblemId`） | **1** |

**对照实验**（同一账号 / 同一题 / 同一时刻，仅该字段不同）：

| `contestProblemId` 取值 | HTTP 结果 |
|---|---|
| `2098595065671634946`（`p.contestProblemId`） | **200** ✅ |
| `2098595608607510530`（`p.id`，旧写法） | **404** ❌ |

**修复**：脚本改为 `contestProblemId: p.contestProblemId ?? p.id`。修复后 `submit` 错误数
由 **236 → 0**（50 并发档）。

> **重要推论**：F1 是"静默的全量失败"缺陷——不报错、只把每次提交记为 404，极易被误认为
> "服务端容量不足"。F1 + F2 叠加，共同解释了**为什么比赛专属路径在 81 与 82 上都未被真正覆盖**。

#### F2 详述

`ContestService.assertCanView()` 只放行两类访问者：

```java
private void assertCanView(ContestEntity contest) {
    if (canManage(contest)) return;                       // ① 管理员 / 出题人
    if (contest.getStatus() == ContestStatus.PUBLISHED
            && contest.getVisibility() == ContestVisibility.GROUP   // ② 仅 GROUP 可见性
            && isGroupMember(contest.getScopeGroupId(), SecuritySupport.currentUserId())) return;
    throw new DomainException(ErrorCode.FORBIDDEN, "Cannot access contest");
}
```

而 `ContestVisibility` 枚举**只有 `PRIVATE` 和 `GROUP` 两个值，没有 `PUBLIC`**；
`ContestService.create()` 将 `visibility` 初始化为 `null`，Flyway 迁移 `V22` 允许该列为 NULL。

→ **新建比赛的 `visibility` 默认为 `null`，普通学生访问 `/contests/{id}` 与
`/contests/{id}/problems` 必然 403**，即使该学生在该场次已是 `APPROVED + ACTIVE` 参赛者。

**对照**（同一账号、同一比赛）：

| 端点 | 授权依据 | 学生访问 |
|---|---|---|
| `GET /contests/{id}` | `assertCanView()` | ❌ 403 |
| `GET /contests/{id}/problems` | `assertCanView()` | ❌ 403 |
| `GET /contests/{id}/runs/{runId}/open` | 场次参赛资格 | ✅ 200 |
| `GET /contests/{id}/runs/{runId}/problems` | 场次参赛资格 | ✅ 200 |
| `POST /submissions`（带比赛上下文） | `resolveSubmissionContext()` → `requireContest()` | ✅ 不受影响 |

**建议后端修复**：`assertCanView()` 增加"PUBLISHED 且非 GROUP 限制"的放行分支，
或明确要求比赛创建时必须显式设置 `visibility`。

### 10.5 F6 性质澄清（这不是项目缺陷）

`deploy/compose.yml`（本地/dev 用）与 `deploy/compose.production.yml`（生产用）的健康检查
参数**写法不同**：

| 服务 | 本地 `compose.yml` | 生产 `compose.production.yml` |
|---|---|---|
| auth-service | `interval 10s / timeout 5s / retries 12` | **仅 `test:`，未设置任何 interval/timeout/retries/start_period** |
| gateway-service | 同上 | 同上 |
| problem-service | 同上 | 同上 |
| ai-service | 同上 | 同上 |
| judge-worker | 同上 | 同上 |
| mysql | `retries 10` | `interval 10s / timeout 5s / retries 20 / start_period 30s` |
| redis | `retries 10` | `interval 10s / timeout 5s / retries 12` |
| rabbitmq | `retries 10` | `interval 10s / timeout 5s / retries 18 / start_period 20s` |
| sandbox | `retries 5` | `interval 10s / timeout 3s / retries 10 / start_period 10s` |

**事实认定**：
1. 对 F6 的改动**只针对本地 `deploy/compose.yml`**；**从未修改过 81 服务器上的
   `/opt/aioj/compose.production.yml`**，也未重启过任何容器；
2. 生产 compose 中 5 个 JVM 服务的健康检查**只有 `test:` 一行**，其余参数走 Docker 默认值，
   因此**不存在"120s 窗口 < 146s 启动"的问题**；
3. 生产容器自 2026-08-19 启动以来 `RestartCount=0`、`OOMKilled=false`，健康状态正常。

**F6 的准确表述**："**本地开发** compose 的健康检查窗口过短，导致本地 `docker compose up`
时 auth-service 被误判 `unhealthy`、连带 gateway 拒绝启动"——**本地环境可用性问题，非项目缺陷**。

**顺带记录（待办，不属本次压测范围）**：生产 compose 给 mysql / rabbitmq / sandbox 都配了
`start_period`，但 **5 个 JVM 服务一个都没配**。当前容器运行正常，但**冷启动（整机重启、
滚动发布）时 JVM 服务约 150 秒的启动时间没有宽限期保护**，存在启动竞态风险。
建议生产 compose 也为 JVM 服务补 `start_period`（例如 `180s`）。

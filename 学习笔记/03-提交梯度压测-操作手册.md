## 零、先搞懂：这个测试和"登录压测"有什么本质不同

| | 登录压测（已完成） | 本次（提交压测） |
|---|---|---|
| 压力落点 | 只压 auth-service | **压 网关→problem→RabbitMQ→judge→sandbox 整条链** |
| 是否写数据 | 否 | **是，每人 1 条真实提交** |
| 会不会压崩 | 很难 | **会**，尤其是判题队列积压和内存 |

**"服务器崩溃"在这个系统里最可能的四种形态**（你要在监控数据里找它们）：

1. **判题队列积压**：`aioj.judge.queue` 的 `messages_ready` 持续上涨不回落
   → 提交受理快，但判题消费不过来 → 学生永远看到"判题中"
2. **内存打满 / swap 暴涨**：sandbox 每个判题进程都要内存
   → 一旦开始 swap，判题延迟会**几倍放大**，恶性循环
3. **容器 OOM 被杀**：`OOMKilled=true` 或 `RestartCount` 增加
4. **HTTP 5xx / 超时**：网关或上游服务顶不住

> **判题并发是瓶颈的关键参数**：81 上 `JUDGE_CONCURRENCY=2`。
> 意思是最多同时判 2 份代码。50 人同时交 → 队列里会排 50 份，
> 按每份判题 2~8 秒算，**排空可能要几分钟**。这不是 bug，是设计如此。
> **所以"能不能承受"的判据不是"多快判完"，而是"队列能不能最终排空、有没有崩"。**

### 采样表怎么读

| 列 | 含义 | 危险信号 |
|---|---|---|
| `uptime_load1` | 1 分钟负载 | 超过 4（=核数）说明 CPU 排队 |
| `mem_used_mb` / `mem_avail_mb` | 内存 | `avail` < 500 MB 危险 |
| `swap_used_mb` | swap 已用 | **持续上涨 = 危险** |
| `queue_ready` | 判题队列等待数 | 持续上涨不回落 = 判题跟不上 |
| `queue_unacked` | 已投递未确认 | 长期 >0 说明消费者卡住 |
| `dlq` | 死信队列 | **非 0 就是严重问题** |
| `queued_subs` / `running_subs` | 数据库里的待判/判中 | 同上 |
| `auth%` / `judge%` / `sbox%` / `mysql%` | 各容器 CPU | 看谁在抢 |
| `health_gw` / `health_web` | 健康端点 | **非 200 = 服务已经不可用** |

## 七、第六步：跑梯度测试（10 → 30 → 50）

### 梯度设计的原理

**为什么要 10 → 30 → 50，而不是直接 50？**

因为**每次只变一个变量**。如果直接打 50 崩了，你无法判断：
- 是 50 这个量级本身超限？
- 还是 10 人时就已经有问题，只是被掩盖了？

有了梯度，你能画出 **"人数 → 关键指标"的曲线**：
- 如果 10→30→50 是**平滑劣化** → 有余量，能扛
- 如果 30→50 **突然断崖** → 找到了拐点，报告价值极高

先改 `K6_ENV_FILE`/环境变量。**10 人 = 3+3+4 的分布**（都交标程，先不掺 TLE）：

  -e CONTEST_RUN_ID="<你的场次ID>" `
  -e P1_ID="2067578982906073090" -e P1_TOTAL="3" -e P1_TLE="0" -e P1_CONTEST_PROBLEM_ID="<比赛题1>" `

- 提交瞬间冲高 → 正常

- **一直不降 → 判题卡住了，这就是"承受不住"**

## 十一、常见坑（提前说，少走弯路）

| 坑 | 现象 | 处理 |
|---|---|---|
| 比赛未启动 | 提交返回 4xx | 确认 Run 状态是进行中，`startAt` 已过 |
| 参赛者未审批 | 提交被拒 | 后台把 50 人全部审批通过 |
| 用错题目 ID | 提交报错或判题异常 | `CONTEST_PROBLEM_ID` ≠ 题库 `ID` |
| 轮询超时 | k6 报 `did not reach terminal status` | 说明判题太慢/卡住——**这本身就是要记录的发现**，把 `POLL_TIMEOUT_MS` 调大重跑对比 |
| 比赛中途结束 | 后半段提交被拒 | `endAt` 设远一点 |
| 密码带空格 | 登录 401 | 用 `12345678`，别加引号空格 |
| 队列没排空就跑下一轮 | 数据被污染 | 等队列回 0 再跑 |
| 忘了开监控 | 只有 k6 结果，没有服务器侧证据 | **监控必须在压测前启动** |
